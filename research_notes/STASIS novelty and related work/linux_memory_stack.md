# The modern Linux memory-pressure / thrashing stack (through kernel 7.x, 2026)

Scope note: findings below are drawn from current (2026) kernel.org documentation (rendered doc version 7.3.0 at time of reading), freedesktop.org systemd man pages ("latest"), project READMEs, LWN, and Meta engineering material. Where a kernel version of first landing could not be confirmed from a primary source, it is flagged in Gaps.

## PSI: definitions of "some"/"full", trigger windows, minimum window, notification latency, and limits as a thrashing signal

### Takeaway
PSI gives a time-based, aggregate stall metric ("some" = at least one task stalled, "full" = all non-idle tasks stalled, which the kernel docs explicitly call thrashing), with a userspace trigger API whose windows are bounded to 500 ms – 10 s and whose update interval is bounded to 50 ms – 1 s, with at most one notification per window. Its core limitation for a thrashing controller is that it is *by design* not attributable to individual tasks — it tells you that stalling is happening, not who is causing it.

### Cited Findings
- "some" = share of time in which *at least some* tasks are stalled on a resource; "full" = share of time in which *all non-idle* tasks are stalled simultaneously, which the documentation treats as thrashing because CPU cycles go unused — [kernel.org Documentation/accounting/psi](https://www.kernel.org/doc/html/latest/accounting/psi.html)
- Files are `/proc/pressure/{cpu,memory,io}`, each with `some` and `full` lines giving `avg10`, `avg60`, `avg300` percentages plus a `total` in microseconds — [kernel.org psi](https://www.kernel.org/doc/html/latest/accounting/psi.html)
- CPU `full` is "undefined at the system level"; it has been reported since 5.13 and is pinned to zero for backward compatibility — [kernel.org psi](https://www.kernel.org/doc/html/latest/accounting/psi.html)
- Per-cgroup PSI requires `CONFIG_CGROUPS=y` and cgroup2 mounted; each cgroup dir exposes `cpu.pressure`, `memory.pressure`, `io.pressure` in the same format, and per-cgroup monitors behave identically to system-wide ones — [kernel.org psi](https://www.kernel.org/doc/html/latest/accounting/psi.html)
- Trigger API: open the pressure file and write `<some|full> <stall_us> <window_us>` (doc example `some 150000 1000000` = 150 ms stall within a 1 s window), then wait with `poll()`/`select()`/`epoll()` on `POLLPRI`; one trigger per fd, a second write to the same fd fails with `EBUSY`, and closing the fd removes the trigger — [kernel.org psi](https://www.kernel.org/doc/html/latest/accounting/psi.html)
- Kernel-accepted trigger window sizes are **500 ms to 10 s**; the monitoring update interval is **minimum 50 ms, maximum 1 s** (the minimum exists to prevent excessive polling, the maximum is where plain PSI averages are considered sufficient) — [kernel.org psi](https://www.kernel.org/doc/html/latest/accounting/psi.html)
- While a metric is stalled, its growth is checked **10 times per tracking window**; monitors are only active while the system is in the stall state, and an activated monitor stays active for at least one full tracking window to avoid rapid toggling — [kernel.org psi](https://www.kernel.org/doc/html/latest/accounting/psi.html)
- Unprivileged users may create monitors, but the window must be a **multiple of 2 s**, to bound resource use — [kernel.org psi](https://www.kernel.org/doc/html/latest/accounting/psi.html)
- Userspace notifications are **rate-limited to one per tracking window**; the documentation gives no explicit end-to-end notification latency figure — [kernel.org psi](https://www.kernel.org/doc/html/latest/accounting/psi.html)
- PSI requires Linux 4.20 or later (as stated in systemd-oomd's requirements) — [systemd-oomd.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html)
- `cgroup.pressure` (default "1") enables/disables PSI accounting per cgroup; it is **not hierarchical**, and disabling it on deep non-leaf cgroups can reduce overhead — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- PSI does not attribute pressure to individual tasks by design; a 2026 kernel RFC ("psi: Introduce in-kernel PSI auto monitor feature") argues that developers therefore have to reconstruct root cause in userspace by correlating multiple tools, logs or tracing after the fact, and proposes an in-kernel monitor that captures contributing tasks at the exact moment configured thresholds are breached — [RFC PATCH 0/1 psi auto monitor](https://lkml.iu.edu/2607.2/07955.html); [RFC PATCH 1/1](https://lkml.iu.edu/2607.0/04766.html)
- The original 2018 PSI design describes stall states as *aggregate* versions of per-task delay-accounting delays, with samples "averaged across CPUs — weighted by the CPUs' non-idle time and converted to percentages", i.e. per-task detail is gone by the time numbers are exposed — [PSI patch posting, LKML 2018](https://lkml.rescloud.iu.edu/1807.1/04666.html)
- In the same 2026 RFC thread the author concedes that "the task experiencing the stall is not necessarily the root cause" (domain-level pressure point accepted) — [RFC thread](https://lkml.iu.edu/2607.2/07955.html)
- Practitioner complaint: load average is easy to trace back to its sources, whereas it is difficult to work out where PSI numbers come from — [etbe.coker.com.au](https://etbe.coker.com.au/?p=4803)

### Inferences
- A controller using the privileged PSI trigger API has a hard floor on reaction granularity: ~50 ms update interval, ≥500 ms window, one notification per window. So sub-100 ms closed-loop control on PSI notifications alone is not achievable through the documented interface; faster loops require polling the pressure files directly or a different signal.
- Because "full" is defined as *all non-idle tasks stalled*, it is a late, severe signal on a multi-core desktop: a single runnable task hides full pressure. "some" is earlier but noisy. Any thrashing controller needs a victim-attribution mechanism of its own, since PSI deliberately provides none.

### Gaps
- No documented figure for actual notification latency (time from threshold breach to `POLLPRI` wakeup); the docs only bound the window and the rate limit.
- No documented minimum/maximum for the stall-threshold argument itself.
- Merge status of the 2026 in-kernel PSI auto-monitor RFC could not be confirmed; treat it as a proposal only.

## systemd-oomd and ManagedOOMMemoryPressure: policy, what it kills, known complaints

### Takeaway
systemd-oomd is a cgroup-v2 + PSI userspace OOM killer: when a monitored cgroup's memory pressure exceeds a limit (default 60%, configurable per unit) or system swap usage exceeds a limit, it picks a *descendant* leaf cgroup and `SIGKILL`s every process in it. It only kills — there is no pause, throttle, or fairness — and it is widely reported on Fedora and Ubuntu to kill browsers, IDEs and Flatpak apps during moderate pressure.

### Cited Findings
- It is a userspace OOM killer that uses cgroups v2 and PSI to act before the kernel OOM killer; it reads unit settings from systemd at startup, watches for changes, and periodically polls PSI for the system and for monitored cgroups — [systemd-oomd.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html)
- Monitoring is opt-in per unit via `ManagedOOMSwap=` and `ManagedOOMMemoryPressure=`, each `auto` (default) or `kill`; both added in systemd v247. `kill` makes the unit a monitoring candidate; `auto` means its data is not used, though it can still be killed if an ancestor is set to `kill` — [systemd.resource-control(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)
- `ManagedOOMMemoryPressureLimit=` is a percentage 0–100%, default 0% meaning "use the oomd.conf limit"; ignored unless `ManagedOOMMemoryPressure=kill`. Added in v247 — [systemd.resource-control(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)
- `ManagedOOMMemoryPressureDurationSec=` (added in systemd **v257**) overrides the pressure duration per unit; must be empty or ≥ 1 s, default empty = use oomd.conf — [systemd.resource-control(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)
- The man page cites a **default memory-pressure limit of 60%**, suggests it suits less latency-sensitive units such as `system.slice`, and suggests a lower limit such as **40%** for `user@$UID.service` — [systemd-oomd.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html)
- Action: when a limit is exceeded, systemd-oomd selects a cgroup and sends **`SIGKILL` to all processes in it**. Only *descendant* cgroups are candidates — the unit holding the `kill` property is not itself a candidate unless one of its ancestors also has it set. Only leaf cgroups, or cgroups with `memory.oom.group=1`, are eligible — [systemd-oomd.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html)
- `ManagedOOMPreference=` (v248) takes `none` (default) / `avoid` (selected only if no other viable candidate) / `omit` (never a candidate). `avoid`/`omit` need xattr support; for swap-based selection the xattr is only honoured if the cgroup is root-owned, and for pressure-based selection if the cgroup is root-owned or the unit's cgroup and the monitored ancestor share an owner. Not applied recursively; the docs advise using them sparingly — [systemd.resource-control(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html)
- `ManagedOOMSwap=` uses **system-wide** swap values, so the man page suggests setting it on `-.slice` and letting descendants be candidates; swap-based actions are ignored on systems without swap — [systemd-oomd.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html)
- Requirements: full unified cgroup hierarchy (v2), memory accounting on monitored units (e.g. `DefaultMemoryAccounting=true`), kernel ≥ 4.20 for PSI, swap strongly recommended — [systemd-oomd.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html)
- Documented cautions: without swap the system can livelock quickly and pressure rises more abruptly (more tuning needed); enabling monitoring on `user.slice`/`user-$UID.slice` or their ancestors risks killing everything in a session scope — [systemd-oomd.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html)
- Ubuntu's own description of the swap policy: when total system memory usage *and* swap usage both exceed `SwapUsedLimit` (90% by default on Ubuntu), monitored cgroups with >5% swap usage become OOM-kill candidates — [ubuntu-devel, June 2022](https://lists.ubuntu.com/archives/ubuntu-devel/2022-June/042130.html)
- Ubuntu maintainers after enabling it by default in 22.04: "there have been reports of systemd-oomd killing user applications too frequently (e.g. browsers, IDEs, and gnome-shell in some cases)" — [ubuntu-devel](https://lists.ubuntu.com/archives/ubuntu-devel/2022-June/042116.html); corresponding bug "systemd-oomd frequently kills firefox and visual studio code" — [LP #1972159](https://lists.snapcraft.io/archives/foundations-bugs/2022-June/476922.html)
- Fedora Workstation issue #358 "systemd-oomd seems overly aggressive": reporter disabled it on several machines because running a VM or compiling caused oomd to start killing things; closed as fixed, but with later reports of continued over-aggression — [pagure fedora-workstation #358](https://www.pagure.io/fedora-workstation/issue/358)
- Fedora 42/43-era Discourse report of Chrome and Flatpak apps being SIGKILLed after a modest memory spike — [Fedora Discussion](https://discussion.fedoraproject.org/t/system-d-oomd-killing-flatpak-too-fast/172933)
- 2021 Fedora 34 rollout report: "early issues have revolved around initial limits for initiating the OOM killing being too low, swap killing being too aggressive, and high CPU resources" — [Phoronix](https://www.phoronix.com/news/systemd-oomd-2021)
- `-n`/`--dry-run` logs kills instead of performing them; `SIGHUP` reloads oomd.conf — [systemd-oomd.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html)

### Inferences
- `ManagedOOMPreference=` is a static priority/exclusion list, not fairness: it reorders or removes candidates but never bounds how often a given workload is victimised, and provides no way to give a workload a later turn rather than death.
- Because candidates must be leaves (or `memory.oom.group` cgroups) and the monitored unit itself is exempt, oomd's resolution is the systemd unit/scope boundary. Workloads not run under their own unit (e.g. processes launched directly inside a session scope) are killed as a whole group — which is exactly the Fedora/Ubuntu "lost my whole session" class of complaint.

### Gaps
- The man page does not state the default pressure *duration* or which PSI average (avg10/avg60) is used; oomd.conf(5) was not fetched, so `DefaultMemoryPressureLimit`, `DefaultMemoryPressureDurationSec` and `SwapUsedLimit` upstream defaults are unverified here (the 90% `SwapUsedLimit` figure above is Ubuntu's statement, not upstream's).
- No primary source found for the exact victim *ranking* function within eligible candidates.

## earlyoom, nohang, thrash-protect: signal, action, fairness, self-reported gaps

### Takeaway
earlyoom and nohang **kill** (SIGTERM escalating to SIGKILL) on free-memory/swap thresholds — nohang can also use PSI; thrash-protect is the only one of the three that **pauses** (SIGSTOP/SIGCONT) on a swap-activity signal. None implements admission control, and thrash-protect explicitly states it "is not optimized to be 'fair'", with a roadmap that still only *aspires* to read `/proc/pressure/memory`.

### Cited Findings — earlyoom (KILLS)
- Signal: kernel `MemAvailable` plus free swap, polled "up to 10 times a second (less often if there is a lot of free memory)"; PSI is **not** an input — it appears only in "See also", pointing at oomd — [earlyoom README](https://github.com/rfjakob/earlyoom)
- Trigger: *both* available memory and free swap must fall below the threshold, default **10%** of total memory; `-m`/`-s` set percentages, `-M`/`-S` set KiB — [earlyoom README](https://github.com/rfjakob/earlyoom)
- Action: "sends SIGTERM once below PERCENT, then SIGKILL once below KILL_PERCENT (default PERCENT/2)". No SIGSTOP. `-P`/`-N` run scripts before/after a kill; `--dryrun` disables killing — [earlyoom README](https://github.com/rfjakob/earlyoom)
- Victim: highest `oom_score` by default, or largest RSS with `--sort-by-rss`; `--prefer`/`--avoid`/`--ignore` take regexes, `--ignore-root-user` skips root processes, `-g` kills whole process groups, and `oom_score_adj=-1000` processes are skipped — [earlyoom README](https://github.com/rfjakob/earlyoom)
- No fairness, quota, or admission-control mechanism is described anywhere in the README; the stated design goal is to be "simple and solid", pure C with no dependencies — [earlyoom README](https://github.com/rfjakob/earlyoom)

### Cited Findings — nohang (KILLS)
- Signals: `MemAvailable` (Linux 3.14+), `SwapFree`, zram `mem_used_total`, **PSI metrics** (requires Linux 4.20+ with `CONFIG_PSI=y`), and optionally kernel messages for OOM events — [nohang README](https://github.com/hakavlad/nohang)
- Action: **SIGTERM by default**, escalating to **SIGKILL** if the victim does not exit and memory keeps dropping; SIGTERM can be replaced by a per-match custom command (e.g. restart a service, `kill -INT`). SIGSTOP is not mentioned — [nohang README](https://github.com/hakavlad/nohang)
- PSI support exists with soft/hard threshold config sections; the README does not document threshold semantics or default values — [nohang README](https://github.com/hakavlad/nohang)
- Victim selection: a "badness" score adjustable by regex matching on process name, cgroup, exe realpath, environment variables, cmdline, and effective UID; `--tasks` shows badness, oom_score, oom_score_adj. The badness formula is not given in the README — [nohang README](https://github.com/hakavlad/nohang)
- No fairness or admission control described — [nohang README](https://github.com/hakavlad/nohang)
- Self-stated limitations: the documentation is "terrible" (author's word); ZFS ARC cache does not count toward `MemAvailable`; kernels without `CONFIG_CGROUP_CPUACCT=y` report **incorrect PSI metrics**; it runs as root with access to all process memory and user data; some settings can cause unwanted kills; "not a panacea" with no universal settings — [nohang README](https://github.com/hakavlad/nohang)

### Cited Findings — thrash-protect (PAUSES; the closest prior art)
- Signal: swap activity from `/proc/vmstat` (`pswpin`, `pswpout`) — **not** major page faults. A product-style formula roughly (swapin+ε)·(swapout+ε) > threshold, so heavy one-way or lighter two-way swapping both trigger. Disk swap pages are weighted 128× (HDD) or 8× (SSD) relative to zswap pages; zram is weighted like zswap when it is the only swap device — [thrash-protect README](https://github.com/tobixen/thrash-protect)
- The README says `/proc/pressure/memory` "will probably be used" in future — i.e. it does **not** use PSI today — [thrash-protect README](https://github.com/tobixen/thrash-protect)
- Action: sends **SIGSTOP** (`kill -STOP`) to the chosen process. When swapping stops it SIGCONTs **one** stopped process; if swapping restarts, the last resumed PID is re-frozen. It writes a file in /tmp while processes are frozen so NRPE can monitor it — [thrash-protect README](https://github.com/tobixen/thrash-protect)
- Victim selection, three algorithms tried in order: (1) last-unfrozen PID if still running; (2) `oom_score` — drawback: it does not reflect *current* behaviour and favours parent PIDs; (3) page-fault count — drawbacks: misses write-only memory growth, gives false positives, and needs per-process state that can itself be swapped out — [thrash-protect README](https://github.com/tobixen/thrash-protect)
- Fairness, stated outright: "Thrash-protect is not optimized to be 'fair'." One process may flap while another runs at 100%. Frozen-list handling is heuristic: "get from the head of the list sometimes, pop from the tail most of the times." Black/whitelisting works by **weighting the suspension score, not as hard rules**, and whitelisting does not keep pages resident — [thrash-protect README](https://github.com/tobixen/thrash-protect)
- Roadmap, before 1.0 (**should**): "Support configuration through command line switches as well as through a config file"; "Graceful handling of SIGTERM (any suspended processes should be reanimated)"; "Recovery on restart (read status file and resume any suspended processes)" — [thrash-protect README](https://github.com/tobixen/thrash-protect)
- Roadmap, before 1.0 (**may**): unit tests; lower memory use; "Read performance statistics from /proc/pressure/memory if it exists" — [thrash-protect README](https://github.com/tobixen/thrash-protect)
- Roadmap, 2.0: "Rewrite to C for better control of the memory footprint" and "Rely on /proc/pressure/memory to exist" — [thrash-protect README](https://github.com/tobixen/thrash-protect)
- Known problems: parent/child job-control breakage (suspending a child can suspend its parent — documented for `sudo`, where the parent must be resumed manually; bash backgrounding of foreground jobs; interactive programs staying suspended after resume); swap space is required and performance is poor without it; "Thrash-protect is optimized for servers, not desktops" and GUI sessions may not work during heavy thrashing; it is not real-time safe; `mlockall` use "should be made optional" and the tool can use significant memory on small hosts; a terminal can become unusable under pressure *without* being stopped because whitelisting does not keep its code resident — the README suggests `memory.min`/`MemoryMin=` as a possible fix that thrash-protect does not currently offer; zram-only benefit is still being evaluated (issue #27), and zram can push the kernel into evicting file pages and freezing the box — [thrash-protect README](https://github.com/tobixen/thrash-protect)
- Source inconsistency worth flagging: the README's update section says version 1.0 was released 2026-02-10, yet the roadmap still lists items to be done "before 1.0"; the README also points at `docs/TODO.md` which the author admits has not been kept up to date — [thrash-protect README](https://github.com/tobixen/thrash-protect)

### Inferences
- Kill vs pause split is clean: **earlyoom, nohang, systemd-oomd kill; thrash-protect pauses** (and the new rtux, below, pauses). Nothing in this set does admission control.
- thrash-protect is the single closest prior art to a freeze-based thrashing controller, and its own README concedes the three things a rigorous design would have to fix: no fairness guarantee, no PSI input, and no protection (memory.min) for the pieces that must stay responsive. Its reliance on raw `pswpin`/`pswpout` also means it cannot detect thrashing of the *file* cache without swap traffic.
- Its parent/child SIGSTOP hazards are a structural argument for `cgroup.freeze` over SIGSTOP: the cgroup-v2 freezer stops a whole cgroup via jobctl-stop extension rather than a deliverable signal, so there is no job-control leakage to the parent shell.

### Gaps
- nohang's badness formula and PSI default thresholds are not in the README; not retrieved from the config file.
- thrash-protect's `docs/TODO.md` contents were not retrieved (author says it is stale anyway).
- No systematic trawl of the three projects' issue trackers was possible within the research budget; the limitation lists above are README-sourced plus the one issue (#27) the README cites.

## MGLRU: what it changes, and whether it exposes a per-cgroup working-set signal

### Takeaway
MGLRU (merged in **Linux 6.1**, 2022) replaces the two-queue LRU with multiple generations ordered by access recency, and *does* expose a per-memcg, per-node working-set histogram via `/sys/kernel/debug/lru_gen` — but that interface is debugfs and documented as experimental, its thrashing-prevention knob (`min_ttl_ms`) is off by default, and as of March 2026 LWN reports MGLRU development has stalled with at least one developer calling for its removal.

### Cited Findings
- MGLRU was merged for the **6.1** kernel, described by LWN's merge-window summary as replacing the kernel's two-queue LRU with a multi-stage structure — [LWN 6.1 merge window (via search)](https://lwn.net/Articles/910608); [Phoronix "MGLRU Merged For Linux 6.1"](https://www.phoronix.com/news/MGLRU-In-Linux-6.1)
- It landed requiring the `LRU_GEN` Kconfig option, "not yet flipped on by default" in 6.1 — [Phoronix](https://www.phoronix.com/news/MGLRU-In-Linux-6.1)
- Kernel docs: it is an alternative LRU implementation that "optimizes page reclaim" and improves performance under memory pressure, affecting kswapd CPU usage and RAM efficiency — [kernel.org multigen_lru](https://www.kernel.org/doc/html/latest/admin-guide/mm/multigen_lru.html)
- Generations: pages are grouped into generations numbered `min_gen_nr` (coldest) to `max_gen_nr` (hottest); working-set histograms use `MAX_NR_GENS` bins; the two newest generations are not fully aged and are "equivalent to the active list" — [kernel.org multigen_lru](https://www.kernel.org/doc/html/latest/admin-guide/mm/multigen_lru.html)
- Aging/eviction control via debugfs: `+` creates a new generation (`max_gen_nr+1`); `-` evicts generations up to and including `min_gen_nr`, with optional arguments for swappiness (overriding `/proc/sys/vm/swappiness`) and a cap on pages reclaimed; `min_gen_nr` must be < `max_gen_nr-1`. Commands can be chained with `,` or `;` — [kernel.org multigen_lru](https://www.kernel.org/doc/html/latest/admin-guide/mm/multigen_lru.html)
- **Per-cgroup working-set signal:** reading `/sys/kernel/debug/lru_gen` returns a non-cumulative histogram of pages accessed within each `age_in_ms` interval, **per memcg and per node**, split into anon and file pages; the docs state a job scheduler can use this to estimate working sets and rank servers by cold-page size. `/sys/kernel/debug/lru_gen_full` gives extra stats with `CONFIG_LRU_GEN_STATS=y` — [kernel.org multigen_lru](https://www.kernel.org/doc/html/latest/admin-guide/mm/multigen_lru.html)
- Accessed bits in page-table entries can be cleared in batches, controllable via the kill switch — [kernel.org multigen_lru](https://www.kernel.org/doc/html/latest/admin-guide/mm/multigen_lru.html)
- Documented limitations: the debugfs commands are **experimental**; thrashing prevention (`min_ttl_ms`) is **disabled by default**, and larger values risk premature OOM kills; clearing accessed bits in leaf entries may worsen `mmap_lock` contention while disabling it causes a minor slowdown for some workloads; writes to `enabled` have no effect for unsupported hardware components; proactive reclaim can **overestimate cold pages**, so a scheduler may need to retry on another server — [kernel.org multigen_lru](https://www.kernel.org/doc/html/latest/admin-guide/mm/multigen_lru.html)
- Status, March 2026: LWN's "Reconsidering the multi-generational LRU" (Jonathan Corbet, 5 March 2026, previewing LSFMM+BPF 2026) reports progress on MGLRU has stalled and it "still is not enabled on many systems"; some developers want to improve it while "another has called for it to be removed entirely" — [LWN 1060967](https://lwn.net/Articles/1060967/)
- MGLRU reclaim was still being actively reworked in the 7.2 cycle (reclaim loop and dirty-writeback handling reworked; batched young-flag check), with reported gains up to ~30% on MongoDB/YCSB and, with slow I/O, as much as 100% in Phoronix's reporting — [Phoronix "Linux 7.2 MM"](https://www.phoronix.com/news/Linux-7.2-MM)
- Vendor-reported pre-merge figures: Google reported ~47% decrease in app launch time, used on ChromeOS and Android — [Collabora](https://www.collabora.com/news-and-blog/news-and-events/kernel-61-multi-generational-improvements.html) (vendor numbers, treat with caution)

### Inferences
- MGLRU is a usable per-cgroup working-set *estimator* for userspace, but shipping a product on it means depending on an explicitly experimental debugfs interface, in a subsystem whose upstream future was openly questioned at LSFMM+BPF 2026. A design that can fall back to `memory.stat` workingset_* refault counters is safer.
- MGLRU's `min_ttl_ms` is the one in-kernel *thrashing-prevention* knob in this space, and it is off by default and documented as risking premature OOM kills — direct evidence that the kernel does not currently ship a safe thrashing guard.

### Gaps
- The LWN article is paywalled beyond its opening; the actual LSFMM+BPF 2026 session outcome (keep / improve / remove) was not found.
- Whether `LRU_GEN` is now default-on in mainline 7.x could not be confirmed from a primary source.

## DAMON/DAMOS, memory.reclaim, and Senpai-style proactive reclaim

### Takeaway
The kernel now ships a full access-monitoring and proactive-action framework: DAMON monitors access patterns with tunable overhead and DAMOS applies actions (pageout, migrate_hot/cold, stat, …) under time/size quotas, free-memory watermarks and per-cgroup (`memcg`) filters; `memory.reclaim` (Linux **5.19**) gives userspace a direct per-cgroup reclaim lever; and Meta's Senpai drives that lever from PSI in production, reporting 20–32% memory saved per server.

### Cited Findings — DAMON/DAMOS
- Four interfaces: special-purpose kernel builds, the `damo` userspace tool, a sysfs interface for custom tooling, and a kernel-space API. Settings live under `/sys/kernel/mm/damon/admin/`; writing `on`, `off`, `commit`, `update_schemes_stats` to `state` controls execution, and `refresh_ms` enables periodic stat updates — [kernel.org DAMON usage](https://www.kernel.org/doc/html/latest/admin-guide/mm/damon/usage.html)
- Monitoring covers virtual address spaces and physical memory via configurable operation sets; users set sampling, aggregation and update intervals and bound the number of monitored regions to control overhead; `intervals_goal` auto-tunes sampling/aggregation toward a target access rate; data-attribute probes with filters allow attribute-based monitoring — [kernel.org DAMON usage](https://www.kernel.org/doc/html/latest/admin-guide/mm/damon/usage.html)
- A DAMOS scheme pairs an access pattern (ranges for region size, access count, age) with an action; documented actions include `pageout`, `migrate_hot`/`migrate_cold` (with a weighted destination node list) and `stat` — [kernel.org DAMON usage](https://www.kernel.org/doc/html/latest/admin-guide/mm/damon/usage.html)
- Quotas cap how much time and memory an action may consume per reset interval; goal-based auto-tuning adjusts the effective size quota toward user targets; prioritization weights rank regions by size, access frequency and age; a failed-action charging ratio is configurable — [kernel.org DAMON usage](https://www.kernel.org/doc/html/latest/admin-guide/mm/damon/usage.html)
- Watermarks activate/deactivate a scheme on a metric such as system free-memory rate, with high/mid/low thresholds in per-thousand units plus a check interval (doc example: start paging out below 50% free, stop above 60% or below 30%) — [kernel.org DAMON usage](https://www.kernel.org/doc/html/latest/admin-guide/mm/damon/usage.html)
- Filters restrict a scheme by type (anonymous pages, **memory cgroup path**, address range, huge page size, monitoring target); a `memcg` filter lets a scheme target or exclude specific cgroups; filters live in `core_filters`/`ops_filters` and the generic `filters` directory is deprecated — [kernel.org DAMON usage](https://www.kernel.org/doc/html/latest/admin-guide/mm/damon/usage.html)
- Results come from `tried_regions` snapshots and the `damon:damon_aggregated` / `damon:damos_before_apply` tracepoints (recordable with perf) — [kernel.org DAMON usage](https://www.kernel.org/doc/html/latest/admin-guide/mm/damon/usage.html)
- `DAMON_RECLAIM` is a static kernel module documented (by 6.1) as intended "for proactive and lightweight reclamation under light memory pressure" — [kernel.org v6.1 DAMON reclaim](https://kernel.org/doc/html/v6.1/admin-guide/mm/damon/reclaim.html)
- DAMON remains under heavy active development in the 7.x series: 75 commits landed in the 7.0 cycle from 12 contributors; 67 DAMON changes landed in 7.1-rc1, including selectable goal-based quota auto-tuning algorithms (with a new "temporal" algorithm for deterministic userspace-controlled DAMOS utilization), `addr_unit` support, more efficient core-layer filters, and strict `min_nr_regions` enforcement; nine DAMON hotfixes landed in 7.0 — [DAMON Release Newsletter v7.0-rc1..v7.1-rc1, LWN 1070248](https://lwn.net/Articles/1070248/); [LKML copy](https://lkml.iu.edu/2602.3/09925.html)
- In flight as of that newsletter: `node_eligible_mem_bp` quota goal (v8, near landing), `DAMOS_COLLAPSE` for THP (hoped for 7.2-rc1), perf-event-based monitoring (RFC v3, blocked on the data-attributes monitoring interface), and three DAMON topics accepted for an LSF/MM/BPF session — [LWN 1070248](https://lwn.net/Articles/1070248/)
- 7.2-cycle additions: pausing and resuming DAMON without losing state, and extension to monitor general data attributes beyond accesses — [Phoronix Linux 7.2 MM](https://www.phoronix.com/news/Linux-7.2-MM)

### Cited Findings — memory.reclaim
- `memory.reclaim` is write-only and available in all cgroups; `echo "1G" > memory.reclaim` triggers reclaim in the target cgroup. The kernel may reclaim more or less than requested, and returns **-EAGAIN** if it reclaimed less — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- Important for a controller: "proactive reclaim does not signal memory pressure, so socket memory balancing normally isn't triggered" — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- It accepts a nested `swappiness` key applying vm.swappiness-style semantics to that reclaim, valid 0–200 or `max`, where `max` reclaims only anonymous memory — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- It landed in **Linux 5.19**: the selftest commit metadata reads `Patch-mainline: v5.19-rc1`, and secondary documentation states the file was introduced in 5.19. It came from Shakeel Butt's per-memcg proactive reclaim series, with selftests by Yosry Ahmed — [per-memcg proactive reclaim series, lore](https://lore.kernel.org/all/YmdQrql2rSMwjmY4@carbon/T/); [selftest patch metadata](https://code.opensuse.org/kernel/kernel-source/blob/055a156a6428eb9e4939e015054fa2b1eafcf2c8/f/patches.suse/0004-selftests-cgroup-add-a-selftest-for-memory.reclaim.patch); [gihyo.jp (secondary)](https://gihyo.jp/article/2026/05/linux_containers-0062)

### Cited Findings — Senpai / TMO
- TMO (Transparent Memory Offloading) is Meta's memory-offloading system across heterogeneous hardware; its kernel mechanism measures lost work due to resource shortage across CPU, memory and I/O in real time — that mechanism is **PSI** — [Meta Engineering, June 2022](https://engineering.fb.com/2022/06/20/data-infrastructure/transparent-memory-offloading-more-memory-at-a-fraction-of-the-cost-and-power/)
- Meta's explicit contrast: unlike prior approaches that use proxy metrics such as **page-fault rates**, PSI tracks the time a job is not making progress due to resource constraints — [Meta Engineering](https://engineering.fb.com/2022/06/20/data-infrastructure/transparent-memory-offloading-more-memory-at-a-fraction-of-the-cost-and-power/)
- **Senpai** is the userspace agent: it uses PSI to decide dynamically how much memory to offload without prior application knowledge, accounting for datacenter hardware heterogeneity, by applying *mild, proactive* memory pressure — [Meta Engineering](https://engineering.fb.com/2022/06/20/data-infrastructure/transparent-memory-offloading-more-memory-at-a-fraction-of-the-cost-and-power/)
- Offloading to swap happens at "subliminal" pressure levels with turnover proportional to file cache, contrasting with swap's traditional emergency-overflow role — [Meta Engineering](https://engineering.fb.com/2022/06/20/data-infrastructure/transparent-memory-offloading-more-memory-at-a-fraction-of-the-cost-and-power/)
- Results: in production since 2021, saving **20–32% of memory per server** across millions of servers (Meta's own reported numbers) — [Meta Engineering](https://engineering.fb.com/2022/06/20/data-infrastructure/transparent-memory-offloading-more-memory-at-a-fraction-of-the-cost-and-power/); peer-reviewed write-up — [ASPLOS'22 TMO paper (NSF PAR copy)](https://par.nsf.gov/servlets/purl/10332477); [CACM research highlight](https://cacm.acm.org/research-highlights/technical-perspective-memory-efficiency-via-offloading-in-warehouse-scale-datacenters)
- Both PSI and Senpai have been upstreamed/open-sourced, Senpai under the `facebookincubator` GitHub organization — [Meta Engineering](https://engineering.fb.com/2022/06/20/data-infrastructure/transparent-memory-offloading-more-memory-at-a-fraction-of-the-cost-and-power/)

### Inferences
- The in-kernel toolkit for *gradual* response to memory pressure (DAMOS quotas + watermarks + memcg filters, `memory.reclaim` with swappiness, MGLRU aging) is now rich, but every action in it is **reclaim/migration**, not scheduling: nothing in DAMON/DAMOS can defer or admit a workload. The gradual-response axis and the admission-control axis are still disjoint upstream.
- Senpai is the strongest existing PSI-driven closed-loop controller, and its control variable is *how much to reclaim*, not *who runs*. It is therefore a baseline for the signal-and-control-loop part of a thrashing controller, not for the fairness/pause part.
- `memory.reclaim` not signalling memory pressure is a sharp practical point: a controller can reclaim without perturbing its own PSI-based input signal.

### Gaps
- Senpai's own repository, its concrete control law, and its documented limitations were not fetched within budget; only Meta's public description was verified.
- The kernel version in which DAMON itself first landed was not confirmed from a primary source (DAMON_RECLAIM documentation exists at least by 6.1; the DAMON_RECLAIM commit is from a 2021 series, consistent with the commonly cited 5.15/5.16 window, but no primary confirmation was obtained).

## cgroup v2: freeze semantics and safety, memory accounting files, and what working-set estimation it enables

### Takeaway
`cgroup.freeze` (Linux **5.2**) stops a whole cgroup subtree by extending jobctl-stop, so frozen tasks remain killable and ptraceable, the freeze is asynchronous with an explicit completion notification, and the frozen state and cumulative frozen time are both observable — which makes it a far safer pause primitive than SIGSTOP. Combined with `memory.current`/`memory.peak`/`memory.swap.current` and the `memory.stat` `workingset_*` refault counters, cgroup v2 supports per-cgroup working-set and thrashing estimation entirely from userspace.

### Cited Findings — cgroup.freeze
- Read-write on non-root cgroups, values "0"/"1", default "0". Writing "1" freezes the cgroup **and all descendants**; their processes stop and stay stopped until explicitly unfrozen. A cgroup is frozen if it or any ancestor is frozen — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- Freezing **may take time**; on completion the `frozen` key in `cgroup.events` becomes 1 and a notification is issued — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- Safety properties: frozen processes **can be killed by a fatal signal**; processes can enter/leave by explicit migration or by racing with `fork()`; a process moved *into* a frozen cgroup stops and one moved *out* runs — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- Tree operations still work: a frozen empty cgroup can be deleted, and new sub-cgroups can be created inside it — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- Observability: `cgroup.events` exposes `frozen`, and `cgroup.stat.local` exposes **`frozen_usec`**, the cumulative time spent between freezing and thawing — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- It landed in the **5.2** cycle (Tejun Heo's `for-5.2` pull includes Roman Gushchin's cgroup2 freezer). The pull message describes it as a separate mechanism from the cgroup1 freezer that works by extending jobctl stop, so "frozen tasks are trapped in jobctl stop until thawed and can be killed and ptraced"; goals included "tasks can be killed, ptrace works, there is no separate controller" — [cgroup for-5.2 merge](https://android-kvm.googlesource.com/linux/+/abde77eb5c66b2f98539c4644b54f34b7e179e6b)
- A known rough edge: a follow-up `for-5.2-fixes` notes the freezer broke `strace` and that a partial workaround went in — [cgroup for-5.2-fixes merge](https://android-kvm.googlesource.com/linux/+/5f3ab27b9eb7f1b97e6d4460ac4e494588e09f0c)
- Internal semantics: the kernel treats a cgroup as frozen only when its freeze flag is set and all its tasks are frozen or stopped, with frozen-task counters maintained per cgroup and propagated to ancestors — [kernel/cgroup/freezer.c](https://grok.dragonflybsd.org/xref/linux/kernel/cgroup/freezer.c?r=9a6b55ac)
- Earlier `freezing()` refactor by Tejun Heo made freezing test active freeze conditions directly rather than a single `TIF_FREEZE` flag, which was described as "racy (nothing prevents race against cgroup freezing) and fragile" — [commit a3201227f803](https://coral.googlesource.com/linux-imx/+/a3201227f803ad7fd43180c5195dbe5a2bf998aa)

### Cited Findings — memory accounting and working-set fields
- `memory.current` (read-only): total memory currently used by the cgroup and descendants — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- `memory.peak` is **read-write**: it reports the highest usage since creation or the last reset, and writing any non-empty string resets it to current usage *for later reads through the same file descriptor* — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- `memory.swap.current` (read-only): total swap currently used by the cgroup and descendants — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- `memory.stat` working-set fields: `workingset_refault_anon` / `workingset_refault_file` (refaults of previously evicted anon/file pages), `workingset_activate_anon` / `workingset_activate_file` (refaulted pages activated immediately), `workingset_restore_anon` / `workingset_restore_file` (pages detected as an active working set before being reclaimed), and `workingset_nodereclaim` (shadow-node reclaims) — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- Protection/throttling knobs: `memory.min` is hard protection — usage within the effective min is never reclaimed, and if no other reclaimable memory exists the OOM killer runs; `memory.low` is best-effort — not reclaimed unless unprotected cgroups have no reclaimable memory; both have effective values capped by ancestors, with overcommitted protection divided in proportion to usage. `memory.high` throttles processes and applies heavy reclaim pressure, never invokes the OOM killer (though the limit can be breached in extreme cases), and opening it with `O_NONBLOCK` skips synchronous reclaim — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- `memory.events` (hierarchical; `memory.events.local` for local-only) reports `low`, `high`, `max`, `oom`, `oom_kill`, `oom_group_kill`, `sock_throttled`, and a change generates a file-modified event — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

### Inferences
- The `workingset_refault_*` counters are the per-cgroup *thrashing* signal cgroup v2 actually provides: refaults of pages that were recently evicted are, by construction, the thrash itself, and unlike PSI they are attributable to a cgroup. A controller can combine `memory.pressure` (when to act) with per-cgroup `workingset_refault_anon/file` deltas (whom to act on), which is exactly the attribution PSI deliberately omits.
- `cgroup.freeze` answers each of thrash-protect's SIGSTOP hazards: no deliverable stop signal to leak to a parent shell, frozen tasks stay killable so a frozen victim is not an unkillable zombie, and `frozen_usec` provides the per-victim accounting a fairness policy would need (cumulative frozen time is the natural fairness currency).
- `memory.peak`'s fd-scoped reset semantics mean two independent agents can each keep their own peak window without interfering — useful for a controller that measures per-episode peaks.
- `memory.min` plus `cgroup.freeze` together provide what thrash-protect's README wishes for (keep the terminal/shell resident while freezing the greedy workload) — but no shipped tool combines them.

### Gaps
- The last ~41k characters of the cgroup-v2 document were not read, so some later sections (e.g. further memory-controller notes) are unverified here.
- `cgroup.freeze`'s interaction with ptrace is asserted by the merge commit message, not by the admin-guide text, which is silent on ptrace.

## Has anyone built admission control or fair rotation on top of cgroup freezing?

### Takeaway
No shipped or upstream system was found that combines memory-pressure detection with fair, rotating, or admission-controlled freezing. The nearest items are a rejected 2011 cgroup-freezer duty-ratio patch, thrash-protect's explicitly unfair SIGSTOP heuristic, and **rtux/`pressured`** — a Rust PSI+cgroup-v2 desktop daemon created in July 2026 that freezes instead of killing but has 0 stars, no releases, and lists admission control as future work.

### Cited Findings
- A targeted search for fair rotation / admission control over cgroup freezing returned no such system; results were kernel source and mailing-list threads — [search summary over containers@ / LKML results](https://lists.linuxfoundation.org/pipermail/containers/2011-February/026553.html)
- The closest kernel-side precedent is a 2011 patch series, "cgroup/freezer: add per freezer duty ratio control", which let a user set a frozen percentage and a period (example: period 5 seconds, frozen duty ratio 90%) — [containers@ v6 posting](https://lists.linuxfoundation.org/pipermail/containers/2011-February/026553.html); [v9 posting](https://lkml.rescloud.iu.edu/1102.3/00712.html)
- It was rejected on design grounds: reviewers said this is a scheduling-policy knob that does not belong in the cgroup freezer and that the cpu cgroup "might be a more natural fit", and that a userspace daemon periodically flipping the cgroup's CPU quota between zero and the group's runnable level could achieve the same without kernel changes — [LKML review thread](https://lkml.iu.edu/hypermail/linux/kernel/1102.1/01350.html)
- **rtux** (daemon name `pressured`): "a legible, reversible memory-pressure daemon for Linux desktops that freezes runaway apps instead of killing them, and tells you what it did" — Rust, cgroups v2 and PSI, created July 2026, 0 stars — [awesome.ecosyste.ms listing](https://awesome.ecosyste.ms/projects/github.com%2Fjustinstimatze%2Frtux); [github.com/justinstimatze/rtux](https://github.com/justinstimatze/rtux)
- rtux's escalation ladder, in order of consequence: **Pin** (keep the app fast), **Cap** (ask it to release memory it is not really using), **Pause** (freeze until you wake it), **Close** (shut it down, the only irreversible action). It runs as a systemd service, requires cgroups v2, and sets memory limits that reset on reboot — [github.com/justinstimatze/rtux](https://github.com/justinstimatze/rtux)
- rtux has a *static priority* notion but no rotation: it protects the cursor and desktop shell first so the interface stays responsive. **Rotation is not mentioned, and the author lists "refusing a load that won't fit before it arrives" (i.e. admission control) explicitly as "the work ahead."** — [github.com/justinstimatze/rtux](https://github.com/justinstimatze/rtux)
- rtux's own stated limitations: pausing heavy apps is blunt when they are your own open work, so the desktop can still feel slow; it does not yet follow your gaze or keep the active window warm while thinning others; frozen windows do not visibly "frost over" (notification only); the control window needs libadwaita ≥ 1.5 so Ubuntu 22.04 users get only the daemon; the top-bar extension appears only after the next login. Status: MIT, 48 commits, no releases, 0 forks, one reported field observation (paused a 1.1 GB browser and kept the desktop responsive) — [github.com/justinstimatze/rtux](https://github.com/justinstimatze/rtux)
- The README does not name the kernel mechanism it uses — it says the app is "freezing it whole and intact" without stating whether that is `cgroup.freeze` or `SIGSTOP`, and gives no numeric PSI thresholds (it references a config file `50-pressured-oomd.conf`) — [github.com/justinstimatze/rtux](https://github.com/justinstimatze/rtux)
- **ZPressD** is an adjacent PSI-driven daemon that does *not* freeze: it detects pressure via PSI and issues `process_madvise(MADV_PAGEOUT)` hints to move cold working sets into compressed RAM — [github.com/netizennemo/zpressd_android](https://github.com/netizennemo/zpressd_android)
- Whole-system SIGSTOP freezing has old precedent with no memory logic: the Perl module `Sys::FreezeThaw` sends SIGSTOP to all processes, parent-process first — [Sys::FreezeThaw](https://metacpan.org/pod/Sys::FreezeThaw)
- The kernel freezer deliberately avoids a real signal because processes must not be able to trap the stop — [LKML 2007 "Remove process freezer from suspend to RAM pathway"](https://lkml.iu.edu/hypermail/linux/kernel/0707.1/0730.html)
- Userspace OOM killers (earlyoom, oomd, systemd-oomd) act by **killing, not freezing** — [search summary / project docs cross-referenced above](https://awesome.ecosyste.ms/projects/github.com%2Fhakavlad%2Fnohang)

### Inferences
- The gap is real and specific: the pause primitive exists and is safe (`cgroup.freeze`, 5.2), the attribution signal exists (`memory.stat` workingset refaults, MGLRU histograms, DAMON), and the detection signal exists (PSI) — but no system found binds them into a policy with (a) bounded per-victim freeze time / rotation fairness or (b) admission control that refuses work before it is admitted. thrash-protect disclaims fairness; rtux lists admission control as future work; systemd-oomd/earlyoom/nohang kill; DAMOS reclaims.
- The 2011 reviewer objection is a design warning worth answering explicitly: duty-cycled freezing can be characterised as a *scheduling* policy, and reviewers argued it belongs in CPU bandwidth control or in userspace. A design that justifies freezing (memory residency) rather than CPU quota as the controlled resource is on stronger ground.
- rtux's existence (July 2026, 0 stars, no releases) means a novelty claim should be phrased as concurrent/independent rather than absent prior art, and its README should be re-checked near publication.

### Gaps
- rtux's `DESIGN.md` was not retrievable; its actual mechanism (cgroup.freeze vs SIGSTOP), thresholds, and whether any rotation exists in code are unverified.
- No LWN article was found specifically covering freeze-based thrashing control; the negative result rests on keyword searching and may miss work published under different terminology (e.g. "memory admission control", "memory overcommit scheduling", HPC job-scheduler literature, which was outside this search budget).
- GitHub issue trackers were not searched exhaustively (no authenticated GitHub search was performed).

## Cross-cutting summary: KILL vs PAUSE vs RECLAIM, and fairness

### Takeaway
Across the current stack, kill, pause and reclaim are implemented by disjoint tools, and exactly zero of them implement fairness or admission control.

### Cited Findings
- **KILL:** systemd-oomd (`SIGKILL` to all processes in a selected descendant leaf cgroup) — [systemd-oomd.service(8)](https://www.freedesktop.org/software/systemd/man/latest/systemd-oomd.service.html); earlyoom (SIGTERM then SIGKILL) — [earlyoom README](https://github.com/rfjakob/earlyoom); nohang (SIGTERM escalating to SIGKILL) — [nohang README](https://github.com/hakavlad/nohang); the kernel OOM killer as the backstop, with `memory.events` `oom_kill`/`oom_group_kill` counters — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- **PAUSE:** thrash-protect (SIGSTOP/SIGCONT, explicitly "not optimized to be 'fair'") — [thrash-protect README](https://github.com/tobixen/thrash-protect); rtux/`pressured` (freeze, mechanism unstated, no rotation, admission control listed as future work) — [github.com/justinstimatze/rtux](https://github.com/justinstimatze/rtux); kernel primitive `cgroup.freeze` with `cgroup.events:frozen` and `cgroup.stat.local:frozen_usec` — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
- **THROTTLE/RECLAIM:** `memory.high` (throttle + heavy reclaim, never OOM-kills) and `memory.reclaim` (explicit per-cgroup reclaim, does not signal memory pressure) — [kernel.org cgroup-v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html); DAMOS `pageout`/`migrate_*` under quotas and watermarks — [kernel.org DAMON usage](https://www.kernel.org/doc/html/latest/admin-guide/mm/damon/usage.html); Senpai (PSI-driven mild proactive pressure, 20–32% memory saved per server at Meta) — [Meta Engineering](https://engineering.fb.com/2022/06/20/data-infrastructure/transparent-memory-offloading-more-memory-at-a-fraction-of-the-cost-and-power/); MGLRU `min_ttl_ms` thrashing prevention, disabled by default — [kernel.org multigen_lru](https://www.kernel.org/doc/html/latest/admin-guide/mm/multigen_lru.html)
- **Fairness mechanisms found:** none. The closest approximations are static priority/exclusion (`ManagedOOMPreference=avoid|omit`, earlyoom `--prefer/--avoid/--ignore`, nohang badness regexes, thrash-protect score weighting, rtux protecting the shell) and the rejected 2011 freezer duty-ratio patch — [systemd.resource-control(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html); [earlyoom README](https://github.com/rfjakob/earlyoom); [nohang README](https://github.com/hakavlad/nohang); [thrash-protect README](https://github.com/tobixen/thrash-protect); [containers@ duty-ratio patch](https://lists.linuxfoundation.org/pipermail/containers/2011-February/026553.html)
- **Admission control:** no implementation found; rtux names it as unbuilt future work — [github.com/justinstimatze/rtux](https://github.com/justinstimatze/rtux)

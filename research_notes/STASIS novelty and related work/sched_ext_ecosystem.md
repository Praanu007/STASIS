# The sched_ext (BPF pluggable scheduler) ecosystem as of 2026, and whether any scheduler uses memory / page-fault signals

> Research conducted 2026-10-23. Primary sources: kernel.org sched-ext documentation, the sched-ext/scx repository READMEs and issue tracker, sched-ext.com docs, LWN.net, Phoronix, LKML/bpf-next archives, arXiv/ACM DL/USENIX search.
>
> **Methodological caveat that affects every negative claim below:** I was unable to run an exhaustive full-text code search over the scx tree. GitHub's code-search API requires authentication (no `gh` credentials in this environment), grep.app returned HTTP 429, and `deepwiki` for the scx repo also returned 429. The negative findings therefore rest on: the kernel documentation, the scx repository's own README files, the sched-ext.com scheduler documentation, LWN/Phoronix coverage, the LPC 2025 sched_ext microconference material, and multiple targeted web searches for `maj_flt` / page faults / PSI in combination with sched_ext and BPF schedulers. See the **Gaps** sections for exactly what remains unverified and the one command that would close it.

## Q1. Current state of sched_ext upstream (kernel version, API, watchdog, SCX_KICK_PREEMPT, DSQs, vtime)

### Takeaway
sched_ext landed upstream in Linux 6.12 and by the 7.x era is an actively evolving, in-tree scheduler class with a stable-ish `struct sched_ext_ops` struct_ops interface, dispatch queues (DSQs) as the core data structure, optional vtime-ordered insertion, and a runnable-task-stall watchdog that ejects a misbehaving BPF scheduler and falls back to the default scheduler. The documented API nowhere mentions memory or page faults.

### Cited Findings
- sched_ext "is supported by the upstream kernel starting from version 6.12" and is "fully upstreamed as of 6.12"; a kernel must be built with `CONFIG_SCHED_CLASS_EXT=y` plus BPF options (the repo ships a reference `kernel.config`) — [sched-ext/scx README](https://raw.githubusercontent.com/sched-ext/scx/main/README.md)
- The interface is `struct sched_ext_ops`, a BPF struct_ops whose callbacks are all optional except `ops.name`. Documented callbacks include `select_cpu`, `enqueue`, `dispatch`, `dequeue`, `running`, `stopping`, `tick`, `runnable`, `quiescent`, `init_task`, `enable`, `disable`, `exit_task`, `exit`, plus `set_weight` and `cgroup_init` / `cgroup_set_*` for cgroup CPU-controller settings — [Extensible Scheduler Class, kernel.org](https://www.kernel.org/doc/html/latest/scheduler/sched-ext.html)
- DSQs serve as both FIFO and priority queues. Built-ins are one global FIFO (`SCX_DSQ_GLOBAL`) and a per-CPU local queue (`SCX_DSQ_LOCAL`); custom DSQs are created/destroyed with `scx_bpf_create_dsq()` / `scx_bpf_destroy_dsq()`; tasks are placed with `scx_bpf_dsq_insert()` and pulled with `scx_bpf_dsq_move_to_local()` — [kernel.org sched-ext.html](https://www.kernel.org/doc/html/latest/scheduler/sched-ext.html)
- Priority (vtime) dispatch is done with `scx_bpf_dsq_insert_vtime()`; the `scx_userland` example implements a simple vruntime scheduler in user space — [kernel.org sched-ext.html](https://www.kernel.org/doc/html/latest/scheduler/sched-ext.html)
- The documentation states that default scheduling behaviour is restored when an error is detected or "a runnable task stalls", and describes a bypass mode with two module parameters for load/error recovery — [kernel.org sched-ext.html](https://www.kernel.org/doc/html/latest/scheduler/sched-ext.html)
- The watchdog in practice: scx issue #3878 reports `scx_bpfland` "evicted by the sched_ext watchdog" under hackbench on a 128-thread EPYC, as a runnable-task stall where the watchdog missed its check-in for ~5 s while CPUs were idle — [scx issue #3878](https://github.com/sched-ext/scx/issues/3878)
- A `scx_cosmos` stall log shows `runnable task stall`, a kworker that failed to run for ~7 s, and a stack trace through `scx_watchdog_workfn` — [scx issue #3247](https://github.com/sched-ext/scx/issues/3247)
- SCHED_EXT tasks confined to a CPU saturated by RT tasks can trip the stall watchdog and eject the scheduler; a feature request asks for the watchdog to be aware of RT tasks on runqueues — [scx issue #1202](https://github.com/sched-ext/scx/issues/1202)
- Kick semantics: `SCX_KICK_WAIT` returns once the target CPU's current SCX task switches out and has no effect if that CPU isn't running an SCX task; a `sched_ext/for-7.3` patch notes that pairing `SCX_KICK_PREEMPT` with `SCX_KICK_WAIT` on every RT wakeup would make the kicking CPU wait through RT bursts — [stable 6.19 SCX kick fixes](https://ratatoskr.run/stable/2026/01/7127515/t); [sched_ext/for-7.3 patch](https://ratatoskr.run/sched-ext/2026/07/17280021/t)
- A third-party scheduler author reports that combining an idle-CPU test, `SCX_KICK_PREEMPT`, and a `SCX_DSQ_LOCAL_ON` insert from `enqueue` froze his scheduler within ~1 s (watchdog fired at 30 s), while the same pattern from `select_cpu` ran indefinitely; and that pinned per-CPU kthreads cannot migrate, so inserting them into the wrong CPU's local DSQ stalls the scheduler — [r4debox/scx_soup](https://github.com/r4debox/scx_soup) (single developer's account, not a verified kernel diagnosis)
- 2026 roadmap (Andrea Righi, NVIDIA, presented at Linux Plumbers Conference 2025): hierarchical schedulers, improvements to the built-in sched_ext scheduler, composable schedulers, rewriting some C in Rust, **GPU awareness**, **energy-aware abstractions**, and BPF hot-path optimizations. Memory awareness is not on the published roadmap — [Phoronix, sched_ext future plans 2026](https://www.phoronix.com/news/sched-ext-future-plans-2026); [LPC 2025 sched_ext MC](https://lpc.events/event/19/sessions/229/)
- Production use: Meta runs `scx_lavd` on its servers and its engineers have discussed using sched_ext to speed up AI-training fleets — [Phoronix](https://www.phoronix.com/news/sched-ext-future-plans-2026)
- Upstreaming posture for the schedulers themselves: most schedulers were deliberately moved out of the kernel tree into the separate GitHub repository and "are not intended to become part of the kernel sources" — [What's scheduled for sched_ext, LWN](https://lwn.net/Articles/974387/)
- The C example schedulers (e.g. `scx_simple`, "a simple global vtime scheduler" that works acceptably on simple CPU topologies) have been moved out of the main scx repo into `scx-c-examples` and the kernel's `tools/sched_ext` — [scx README](https://raw.githubusercontent.com/sched-ext/scx/main/README.md); [scheds/README.md](https://raw.githubusercontent.com/sched-ext/scx/main/scheds/README.md)

### Inferences
- The watchdog is the single hardest engineering constraint on any new scheduler that wants to do extra per-task work (e.g. reading and accumulating fault counters) in hot callbacks: it does not police CPU time spent inside the BPF callbacks directly, it polices whether *runnable tasks get to run*. Any back-off/throttling policy that deliberately withholds CPU from a task must stay well inside the stall window or it will be ejected — the issues above show real schedulers being ejected at ~5-7 s of starvation.
- The documented API exposes no memory-related callback or hook whatsoever (no fault hook, no reclaim hook, no PSI accessor). A memory-aware sched_ext scheduler must therefore derive its memory signal itself, either by reading task fields from BPF or by importing data from user space — there is no first-class kernel-provided path.

### Gaps
- The kernel.org HTML documentation page I fetched (built from the 7.3 tree) does not name a watchdog mechanism explicitly nor mention `SCX_KICK_PREEMPT`; those details come from patch threads and issue reports. The exact default of `scx_watchdog_timeout` was not confirmed from an authoritative kernel source — the sched_ext source (`kernel/sched/ext.c`, `ext_internal.h`) would settle it. [Codebrowser's ext_internal.h](https://codebrowser.dev/linux/linux/kernel/sched/ext_internal.h.html) was surfaced in search results but not fetched.
- I did not establish which kernel release corresponds to the "7.0 era" feature set specifically; sources discuss 6.19, 7.3 and 7.4 branches without a consolidated per-release feature table.

## Q2. The notable schedulers in scx, and what signal drives each — does ANY read memory pressure, page faults, PSI, or cgroup memory state?

### Takeaway
The scx tree as of 2026 ships ~16 Rust-userspace schedulers. Every documented decision signal is a *CPU-domain* signal: runtime, wakeup/blocking behaviour, latency criticality, CPU topology (LLC / P-vs-E core / NUMA node), load, and static classification by cgroup/comm. **No scheduler in the scx tree is documented as reading memory pressure, page-fault counters, PSI, or cgroup memory state.** The only memory-adjacent concepts present are (a) cache/NUMA *locality* domains and (b) BPF arena memory used as scheduler scratch storage — neither of which is a memory-pressure signal.

### Cited Findings
- The current Rust scheduler roster in `scheds/rust/`: `scx_beerland`, `scx_bpfland`, `scx_flash`, `scx_cake`, `scx_chaos`, `scx_cosmos`, `scx_eevdf`, `scx_forge`, `scx_lavd`, `scx_layered`, `scx_mitosis`, `scx_pandemonium`, `scx_p2dq`, `scx_rustland`, `scx_rusty`, `scx_tickless`; the docs sidebar also lists `scx_wd40`, and `scx_rlfifo` appears in the docs index — [scheds/rust/README.md](https://raw.githubusercontent.com/sched-ext/scx/main/scheds/rust/README.md); [sched-ext.com Rust schedulers index](https://sched-ext.com/docs/scheds/rust)
- `scx_rusty`: hybrid design — load balancing and statistics in user-space Rust, hot-path decisions in BPF; partitions CPUs into scheduling domains, one per last-level cache, and keeps threads in their original domain where possible — [openSUSE Pluggable CPU schedulers](https://en.opensuse.org/Pluggable_CPU_schedulers); [LWN 974387](https://lwn.net/Articles/974387/)
- Per LWN's report of the sched_ext talk, the metrics in play for the deadline-style schedulers are: how long a task actually ran (rather than its static slice), and whether a task mostly blocks on others (consumer), wakes others (producer), or both; virtual deadlines are adjusted on that basis and time slices shortened when the system is overloaded — [LWN 974387](https://lwn.net/Articles/974387/) (note: LWN attributes this to `scx_rusty`; the same behavioural-metric design is what the lavd/flash family is generally described by, so treat the exact attribution with care)
- `scx_lavd`: developed by Igalia, originally for the Steam Deck / gaming; a latency-focused algorithm aiming to minimise latency spikes while keeping throughput and fair CPU-time sharing. Its README names exactly one signal — **how latency-critical a task is** — used to set the task's deadline and time slice; the Rust side supplies CPU topology, and the scheduler builds separate scheduling domains per LLC, per core type (P/E, big/LITTLE), and per NUMA node. The README **does not mention memory, page faults, or memory pressure** — [scx_lavd README](https://raw.githubusercontent.com/sched-ext/scx/main/scheds/rust/scx_lavd/README.md); [openSUSE wiki](https://en.opensuse.org/Pluggable_CPU_schedulers)
- `scx_layered`: statically configured; threads are classified into "layers" by criteria such as executable name, cgroup, or other metadata, each layer getting its own policy, driven by JSON configuration with matching rules. Meta reportedly uses it for web workloads — [LWN 974387](https://lwn.net/Articles/974387/); [DeepWiki scx scheduler implementations](https://deepwiki.com/sched-ext/scx/3-scheduler-implementations)
- `scx_rustland`: makes most scheduling decisions in user-space Rust — [scx README](https://raw.githubusercontent.com/sched-ext/scx/main/README.md); [LWN 974387](https://lwn.net/Articles/974387/)
- The repo's own `scheds/README.md` and `scheds/rust/README.md` contain **no occurrence of memory, page fault, PSI, NUMA, cache, or pressure** in their scheduler descriptions — [scheds/README.md](https://raw.githubusercontent.com/sched-ext/scx/main/scheds/README.md); [scheds/rust/README.md](https://raw.githubusercontent.com/sched-ext/scx/main/scheds/rust/README.md)
- sched_ext's own motivation material does cite a *memory-bandwidth* anecdote — Google's low-priority workloads hogging memory bandwidth and hurting higher-priority work — as a class of problem sched_ext could address, but this is memory *bandwidth* contention, not paging, and is presented as motivation rather than as an implemented policy — [sched-ext.com Overview](https://sched-ext.com/docs/OVERVIEW)
- Memory appears in the kernel docs' examples only as scheduler scratch storage: `scx_sdt` demonstrates BPF **arena** memory management for per-task data, and `scx_qmap` uses arena-backed linked lists — [kernel.org sched-ext.html](https://www.kernel.org/doc/html/latest/scheduler/sched-ext.html)
- Memory pressure appears in the scx tracker only as a *failure* context, not a signal: issue #370 reports a kernel oops while the system was under high memory pressure, with the reporter unsure whether memory pressure was causal — [scx issue #370](https://github.com/sched-ext/scx/issues/370)
- A third-party community sched_ext scheduler, `scx_soup`, "dynamically detects load type (low-latency streams vs batch compute) and routes each task accordingly" — again a CPU-behaviour signal, with no memory input — [r4debox/scx_soup](https://github.com/r4debox/scx_soup)
- A sched_ext proof-of-concept write-up on pacing batch workloads lists the metrics it tracks: **PSI for CPU and I/O**, iowait, and dirty-memory writeback. This is the closest thing I found to pressure-aware sched_ext work, but it is a blog-level engineering PoC, the PSI used is CPU/IO (not memory), and PSI is consumed in the user-space pacing layer rather than being read inside the BPF scheduler — [Pacing Batch Workloads with Linux sched_ext (DEV.to)](https://dev.to/xsub/pacing-batch-workloads-with-linux-schedext-an-engineering-poc-2chf)

### Inferences
- The ecosystem has converged on a consistent signal vocabulary — runtime/slice consumption, wake and block patterns, latency criticality, topology domains, load — and treats the memory subsystem as out of scope. The design axis that *is* being actively extended for 2026 is accelerators and energy, not memory.
- `scx_layered`'s cgroup *matching* is sometimes mistaken for cgroup-memory awareness. It matches on cgroup identity to classify tasks; nothing in its documented design reads `memory.current`, `memory.pressure`, `memory.events` or any other memcg state.
- Because LLC/NUMA domains are pervasive in scx, a reviewer may push back that scx is "already memory-aware". The precise distinction a thesis should draw: scx is *memory-hierarchy-locality-aware* (where a task's cache lines are), and nowhere *memory-capacity- or paging-aware* (whether the task's working set fits).

### Gaps
- I could not verify per-scheduler internals for `scx_flash`, `scx_bpfland`, `scx_cosmos`, `scx_p2dq`, `scx_cake`, `scx_chaos`, `scx_mitosis`, `scx_tickless`, `scx_eevdf`, `scx_forge`, `scx_beerland`, `scx_pandemonium`, `scx_wd40` from primary sources. The repo README states explicitly that the real documentation is "the header comment in each `main.rs` or `*.bpf.c` file"; those files were not retrieved (rate limits). The one-line descriptions on the docs index pages are empty.
- DeepWiki's scheduler comparison matrix (`deepwiki.com/sched-ext/scx/1.2-scheduler-comparison-matrix`) would be the quickest consolidated per-scheduler signal table; it returned HTTP 429 and should be retried.

## Q3. Does any published sched_ext scheduler do memory-aware scheduling, NUMA/tiering-aware placement, or back tasks off under memory pressure?

### Takeaway
Yes for NUMA/tiering-aware *placement*, and there is exactly one paper I found that builds a memory-aware sched_ext scheduler — **CXLAimPod** — but it is bandwidth/PMU-driven CXL placement, not paging-driven. I found **no** published sched_ext scheduler that backs tasks off under memory pressure, and none that uses page faults.

### Cited Findings
- **CXLAimPod (arXiv 2508.15980, August 2025)** implements "an eBPF-based scheduler on the Linux 6.14+ sched_ext framework" using cgroup-based hints for application-aware optimisation. Its thesis is that existing OSes and their memory schedulers, designed for a half-duplex world, are unaware of CXL's duplex capabilities; its characterisation reports CXL achieving 55-61% bandwidth improvement at balanced read-write ratios vs DDR5. The scheduler is described as *complementing* NUMA-aware schedulers by fine-tuning CPU selection within a NUMA node — [CXLAimPod, arXiv](https://arxiv.org/html/2508.15980v1) ([PDF](https://www.arxiv.org/pdf/2508.15980)); a secondary summary describes it as using cgroup hints and **per-task PMU counters** to steer read/write-balanced tasks onto CXL links — [CXL-aware allocation overview](https://www.emergentmind.com/topics/cxl-aware-allocation)
- NUMA/LLC/core-type domain construction is standard across scx (`scx_lavd`, `scx_rusty`) — i.e. locality-aware *placement* is thoroughly covered territory — [scx_lavd README](https://raw.githubusercontent.com/sched-ext/scx/main/scheds/rust/scx_lavd/README.md); [openSUSE wiki](https://en.opensuse.org/Pluggable_CPU_schedulers)
- Adjacent non-sched_ext memory-tiering systems that *do* react to memory contention, useful as related work framing:
  - **Tiresias** throttles best-effort workloads' bandwidth when local contention is detected and migrates less-used pages to CXL memory to relieve contention — [Tiresias, ACM](https://dl.acm.org/doi/fullHtml/10.1145/3674399.3674411)
  - **Mercury** (QoS-aware tiered memory) finds that beyond a point, pushing more to CXL degrades latency-sensitive performance when a bandwidth-hungry neighbour is placed on CXL — [Mercury, arXiv](https://arxiv.org/pdf/2412.08938)
  - **NeoMem** is a HW/SW co-design whose NeoProf unit analyses LLC misses to CXL memory and hands the OS page hotness and memory-bandwidth-utilisation data — [NeoMem, arXiv](https://arxiv.org/pdf/2403.18702)

### Inferences
- CXLAimPod is the single most important piece of prior art for a "memory-aware sched_ext scheduler" claim, and a thesis must cite and distinguish it. The distinction is clean and defensible: CXLAimPod's signal is **memory-bandwidth/duplex characteristics measured via PMU counters plus static cgroup hints**, and its action is **placement** (CPU selection within a NUMA node to exploit interconnect properties). It is not a capacity/thrashing signal, it does not read fault counters, and it does not throttle or back off tasks.
- The Tiresias/Mercury/NeoMem line shows the *idea* of throttling under memory contention is well established in memory-tiering research — but implemented in the memory manager, a userspace controller, or hardware, not inside a pluggable CPU scheduler.

### Gaps
- CXLAimPod is an arXiv preprint; I did not verify peer-review status, nor whether its scheduler code is public or present anywhere in the scx tree.
- I did not find any sched_ext scheduler in or out of tree whose policy is "reduce a task's CPU share because it is paging". Absence here is from targeted searching, not from an exhaustive repository grep.

## Q4. Can BPF in sched_ext read `p->maj_flt` and per-task memory state? Verifier constraints? Precedent for exporting per-process stats to userspace via a BPF map?

### Takeaway
Reading `p->maj_flt` from a sched_ext callback should be legal — it is a scalar field read on a struct_ops callback argument, which the verifier treats as a trusted `PTR_TO_BTF_ID` — and exporting per-task counters to user space through a BPF map is the standard, pervasive pattern in scx (every Rust scheduler's userspace half does exactly this for its own stats). I could not find an authoritative source confirming the specific `maj_flt` read, so this should be treated as strongly expected but requiring empirical confirmation on the target kernel.

### Cited Findings
- The kernel kfunc documentation states that pointers passed as tracepoint or **struct_ops callback arguments** count as valid/trusted pointers, as do pointers returned from acquire kfuncs (`KF_ACQUIRE` / `KF_KPTR_GET`) — [BPF Kernel Functions (kfuncs), kernel.org](https://docs.kernel.org/bpf/kfuncs.html)
- Trust does **not** propagate through pointer walks: "any nested pointer that is obtained from walking a PTR_TRUSTED pointer is no longer PTR_TRUSTED", and passing such a nested pointer to a `KF_TRUSTED_ARGS` kfunc is rejected — [PTR_TRUSTED patch series, LKML](https://lkml.rescloud.iu.edu/2211.2/01944.html)
- Recent (2026) verifier work is loosening this: a bpf-next series makes pointers returned from kfuncs trusted by default, and a separate sched_ext patch adds some struct_ops argument fields to a trusted whitelist — [bpf-next: return PTR_TO_BTF_ID...](https://ratatoskr.run/bpf/2026/01/7941401/t); [bpf: sched_ext: Mark ops... (Aug 2026)](https://ratatoskr.run/lkml/2026/08/17436662/t)
- `maj_flt` is a per-task kernel counter held in `task_struct` (`current->maj_flt`, `current->min_flt`) and also exposed per-process via `/proc/$PID/stat` as `majflt` — [nixCraft, viewing page fault statistics](https://www.cyberciti.biz/faq/linux-command-to-see-major-minor-pagefaults/); [Linux memory management: page faults](https://medium.com/@boutnaru/linux-memory-management-part-3-page-faults-2c05f07cf924)
- The standard way to compute a fault *rate* is to sample the counter twice and difference it: "parses `/proc/*/stat`, waits for a period of time, then parses those files again, and compares the results"; the same source notes eBPF tracing (bpftrace) can identify the source of major faults by loading a program into the kernel — [Causes of major page faults](https://www.joyfulbikeshedding.com/blog/2025-02-10-causes-of-major-page-faults.html)
- Precedent for the exact pattern of per-TID fault counters in a BPF map polled by userspace exists as a **proposal, not a documented implementation**: an issue in an unrelated project proposes aggregating minor/major fault counters in a per-TID map with userspace polling deltas, explicitly to avoid per-fault event overhead — [rand-fast issue #24](https://github.com/random6-xyz/rand-fast/issues/24)
- sched_ext itself provides arena-based per-task storage as a first-class example (`scx_sdt` demonstrates BPF arena memory management for per-task data), and every Rust scx scheduler is architecturally split with "statistics" handled in the user-space half — i.e. BPF→userspace stats export is the house style — [kernel.org sched-ext.html](https://www.kernel.org/doc/html/latest/scheduler/sched-ext.html); [openSUSE wiki on scx_rusty](https://en.opensuse.org/Pluggable_CPU_schedulers)
- Relevant BPF constraints flagged in sched_ext discussion: the 512-byte BPF stack limit, kptr support for kernel objects, and a developer request for `alloca()`-style stack allocation in BPF — [LWN 974387](https://lwn.net/Articles/974387/)

### Inferences
- The verifier risk for `p->maj_flt` is low: `p` arrives as a trusted `struct task_struct *` argument to `ops.enqueue` / `ops.running` / `ops.stopping` / `ops.tick`, and `maj_flt` is a direct scalar member of `task_struct`, so no pointer walk and no kfunc argument is involved. The documented restriction that bites is on *nested pointers* (e.g. walking `p->mm->...`, which is both a pointer walk and potentially a kfunc-argument problem) — so reading `p->mm->...` fields or RSS counters is materially riskier than reading `maj_flt`/`min_flt`, and is where a thesis should expect to need CO-RE reads and careful verifier work. CO-RE relocation guidance for such reads is in [Andrii Nakryiko's CO-RE reference guide](https://nakryiko.com/posts/bpf-core-reference-guide/).
- Since `maj_flt` is a monotonic cumulative counter, any in-scheduler use must do its own differencing against a per-task stored previous value and timestamp — which is precisely what arena / task-local storage is for, and which no existing scx scheduler is documented as doing for faults.

### Gaps
- **No source confirms the specific read of `p->maj_flt` inside a sched_ext struct_ops program.** This needs an empirical test (write the probe, load it, read the verifier log) on the target kernel. Treat as unverified.
- I found no published precedent for a *scheduler* exporting per-process page-fault statistics to userspace via a BPF map. The closest is the rand-fast proposal above, which is not a scheduler and not implemented.
- I did not verify which `task_struct` memory fields are safely readable in the 7.x verifier (e.g. `mm->rss_stat` counters, `mm->total_vm`), nor whether any sched_ext-specific kfunc exposes them.

## Q5. Prior art on scheduler-level thrashing response in ANY system (a CPU scheduler that reacts to paging)

### Takeaway
There is deep and well-established classical prior art — the thrashing feedback loop, page-fault-frequency (PFF) replacement, load control / multiprogramming-level adjustment, working-set suspension, and the Linux swap token — plus at least one patent explicitly titled around penalising a task in the scheduler for swapping activity. A thesis cannot claim that "a scheduler reacting to paging" is novel; the defensible novelty is the *mechanism* (doing it in a BPF pluggable CPU scheduler, per-task, at scheduling-decision granularity).

### Cited Findings
- The classical thrashing feedback loop: memory contention makes faulting processes queue on the paging device, CPU utilisation drops, the scheduler reads the drop as idle capacity and admits more processes, worsening contention — [Thrashing (computer science), Wikipedia](https://en.wikipedia.org/wiki/Thrashing_(computer_science))
- Detection convention: a high page-fault rate together with low CPU utilisation is the canonical thrashing signature — [Operating System - Thrashing, TutorialsPoint](https://www.tutorialspoint.com/operating_system/operating_systems_thrashing.htm)
- **Page-fault-frequency (PFF)**: each process has upper and lower fault-rate thresholds; exceeding the upper bound grants more frames, falling below the lower bound releases frames — [Techniques to handle thrashing, GeeksforGeeks](https://www.geeksforgeeks.org/operating-systems/techniques-to-handle-thrashing/)
- **Load control**: the OS adjusts the degree of multiprogramming based on memory utilisation, and a rapid rise in fault frequency is treated as an early warning — [Understanding Thrashing in OS](https://www.scribd.com/document/617778208/Thrashing-Causes-Effect-and-Techniques-to-handle-Thrashing)
- **Working-set suspension**: if combined working sets exceed physical memory, processes are suspended or swapped out to relieve pressure — same source as above
- **Linux swap token**: a token is granted to one faulting process at a time so it can claim extra memory, finish, and release pages; handoff is timestamp-driven. A Linux implementation existed, and a later "preempt" variant added a per-process priority counter tracking swapped-out pages — [Thrashing (computer science), Wikipedia](https://en.wikipedia.org/wiki/Thrashing_(computer_science))
- **Patent: "Scheduler penalty for swapping activity"** (US 9,465,656) — a scheduler that penalises tasks for swapping activity. This is the most direct prior art for the core idea of a CPU scheduler reacting to paging — [US 9465656, USPTO](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9465656)
- Related patents in the same space: "Page faulting and selective preemption" (US 12,067,641), on page-fault-driven preemption (GPU context) — [USPTO](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12067641); "Artificial memory pressure for low memory machine" (US 9,747,028) — [USPTO](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/9747028); and an enterprise-data-warehouse workload manager patent (US 8,627,330) that describes the scheduler feedback loop in detail — [USPTO](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/8627330)

### Inferences
- The strongest framing for a novelty claim is therefore *not* "nobody has made a scheduler react to paging" (demonstrably false since the 1960s-70s, and patented) but: classical load control acted at the *admission/multiprogramming-level* granularity, in a monolithic non-pluggable kernel, with system-wide or coarse per-process signals; the swap token acted in the *memory manager*; and modern Linux has retired the swap token entirely, leaving no scheduler-side paging response in the mainline CPU scheduler. The gap is a *per-task, scheduling-decision-granularity, runtime-loadable, BPF-implemented* paging response — and crucially one that can be measured and evaluated without patching the kernel.
- A thesis should expect a reviewer to raise Denning's working-set/load-control literature and should cite the primary sources directly rather than via the tertiary pages found here.

### Gaps
- My sources for the classical material are predominantly tertiary educational sites (GeeksforGeeks, TutorialsPoint, Scribd, Medium) plus Wikipedia. **These are not citable in a thesis.** The primary works need to be obtained and cited directly: Denning (1968) "Thrashing: its causes and prevention" / working-set model; Chu & Opderbeck on page-fault-frequency replacement; Jiang & Zhang on token-ordered LRU / the Linux swap token; and the kernel commit that removed the swap token from Linux (I did not locate it).
- I did not verify when or in which release the Linux swap token was removed, nor confirm the current mainline position (EEVDF/CFS) that the CPU scheduler consumes no paging signal. Both are load-bearing for the novelty argument and should be checked in the kernel source/history.
- I did not search non-Linux systems specifically (VMS swapper, Windows balance set manager, Mach) for their scheduler/pager interaction; these are likely relevant prior art and remain unexamined.

## Q6. Research papers (2023-2026) using sched_ext — anything at OSDI/SOSP/EuroSys/ATC/HotOS?

### Takeaway
sched_ext has begun appearing in top-tier systems venues as *infrastructure* rather than as the object of study: PeeR (OSDI '26) and Aeolia (SOSP '25) both build on it, with a workshop paper (SchedBPF, eBPF '25) and a growing arXiv literature on LLM-agent-generated schedulers. I found **no** paper, at any venue, whose contribution is memory- or page-fault-aware sched_ext scheduling, and no dedicated OSDI/EuroSys paper on sched_ext itself.

### Cited Findings
- **PeeR (OSDI '26)**: makes BPF programs schedulable and preemptable, using sched_ext and cooperative preemption at helper calls; the project repository contains a sched_ext-based scheduler component — [hipersys-team/PeeR](https://github.com/hipersys-team/PeeR)
- **Aeolia (SOSP '25)**: uses sched_ext in a storage stack, to bridge the scheduling semantic gap between userspace and the kernel when using user interrupts — surfaced via [eBPF research papers index (Paul Chaignon)](https://pchaigno.github.io/bpf/2025/01/07/research-papers-bpf.html) and [eunomia.dev papers list](https://eunomia.dev/papers/)
- **SchedBPF (eBPF '25 workshop, ACM)**: on scheduling BPF programs; argues existing approaches (kernel modules with kthreads, userspace daemons, BPF timers) fail to satisfy all requirements for periodic kernel extensions — [SchedBPF, ACM DL](https://dl.acm.org/doi/10.1145/3748355.3748366)
- **SchedCP / "Towards Agentic OS" (arXiv 2509.01245)**: an LLM-agent framework for Linux schedulers; evaluation covers configuring existing schedulers and generating new ones, run on an 86-core Xeon and an 8-core Core Ultra — [arXiv 2509.01245](https://arxiv.org/pdf/2509.01245)
- **Mixture-of-Schedulers (arXiv 2511.11628)**: an adaptive agent that recognises workload patterns and switches between sched_ext policies; states that sched_ext provides the mechanism for policy switching but not the intelligence for when to switch — [arXiv 2511.11628](https://arxiv.org/html/2511.11628v1)
- **SchedBlame (arXiv 2609.02052)**: culprit-attributed CPU contention for containers on stock kernels — adjacent attribution work — [arXiv 2609.02052](https://arxiv.org/pdf/2609.02052)
- **EuroSys '25** eBPF-related work found was on detecting kernel API mismatches for tracing BPF programs, not sched_ext — via [eBPF research papers index](https://pchaigno.github.io/bpf/2025/01/07/research-papers-bpf.html)
- The sched_ext microconference at **Linux Plumbers Conference 2025** is the community's main technical venue for this work — [LPC 2025 sched_ext MC](https://lpc.events/event/19/sessions/229/)
- Practitioner/tutorial literature (not peer-reviewed, but useful for method framing): free5GC's two-part hands-on sched_ext series — [Exploring sched_ext](https://free5gc.org/blog/20250305/20250305/), [Hands-On with sched_ext](https://free5gc.org/blog/20250509/20250509/)

### Inferences
- The publication landscape is favourable: sched_ext is a credible, citable platform in 2026 (OSDI/SOSP uses exist), the LLM-agent papers show the "generate a scheduler for workload X" framing is getting crowded, and the *memory-signal* axis is empty. A thesis occupying "paging-aware sched_ext" is positioned in a gap, not in a crowd.

### Gaps
- Two curated indexes ([pchaigno.github.io](https://pchaigno.github.io/bpf/2025/01/07/research-papers-bpf.html), [eunomia.dev/papers](https://eunomia.dev/papers/)) were surfaced in search but not fetched in full; they are the highest-yield next step for a complete sched_ext/BPF bibliography and should be read directly.
- I did not confirm Aeolia's and PeeR's bibliographic details (authors, exact titles, DOIs) from the proceedings themselves — the venue/year attributions above come from search summarisation and must be verified before citing.
- HotOS: I found no HotOS sched_ext paper, but I did not search the HotOS 2025/2026 programs directly.

## Q7. Work connecting BPF to memory management generally ("BPF for MM")

### Takeaway
"BPF for MM" is an active and fast-moving 2026 topic on LKML with multiple concrete patch series: BPF-driven proactive memcg reclaim (now at v10), a `struct_ops` interface for the memory controller (`memcg_ext`), an extensible-reclaim proposal (`reclaim_ext`), and a research prototype for BPF-based custom page-fault handling (`bpf_fault`). This is strongly supportive context: the kernel community is actively extending BPF into MM, but from the *memory* side — nobody is joining MM signals to the *scheduler* side.

### Cited Findings
- **BPF proactive memcg reclaim** (Hui Zhu): adds a sleepable kfunc `bpf_proactive_reclaim()` performing one proactive reclaim pass on a memory cgroup, making timing and intensity a BPF policy decision. Later revisions restrict it to `BPF_PROG_TYPE_SYSCALL` because the reclaim path can deadlock in filesystem shrinkers when other program types run with filesystem locks held. At v10 as of Sept 2026 — [PATCH bpf-next v10](https://ratatoskr.run/lkml/2026/09/17549861/t); [v7](https://ratatoskr.run/lkml/2026/09/17512804/t); [v6](https://ratatoskr.run/lkml/2026/09/17488880/t)
- **BPF struct_ops for memcg** (RFC v7, same author): introduces BPF `struct_ops` for the memory controller so per-cgroup policies can be customised, plus a kfunc wrapping the cgroup reclaim call; its async-reclaim test reports that with the program attached, the `max` counter does not increase at all in a 32 MB cgroup workload — [RFC PATCH bpf-next v7, mm: BPF...](https://ratatoskr.run/lkml/2026/05/17028790/t)
- **`reclaim_ext`** (LSF/MM/BPF 2026 topic, "Towards Unified and Extensible Memory Reclaim"): proposes merging the traditional LRU and MGLRU eviction paths into one code path with each algorithm supplied as hooks, arguing `mm/vmscan.c` exceeds 8,000 lines with ~40% MGLRU-specific. Gregory Price replies that rewriting MGLRU as an eBPF extension may be the least-worst option for maintenance, while doubting a stable interface would be easy to maintain — [LSF/MM/BPF TOPIC: reclaim_ext](https://ratatoskr.run/lkml/2026/03/3481257/t); [reply thread](https://lkml.iu.edu/hypermail/linux/kernel/2603.3/09647.html); [thread root](https://lkml.iu.edu/hypermail/linux/kernel/2603.3/04703.html)
- **`memcg_ext`** (LSF/MM/BPF 2026 topic, "Reimagining Memory Cgroup") — [LKML thread](https://lkml.iu.edu/hypermail/linux/kernel/2603.1/10792.html)
- **`bpf_fault`**: "It's the Kernel's Fault! Custom Page Fault Handling With bpf_fault", Tal Zussman — a research paper on BPF-programmable page-fault handling — [ACM DL, 10.1145/3830418.3843896](https://dl.acm.org/doi/pdf/10.1145/3830418.3843896) (DL returned HTTP 403 to my fetch; venue/year and abstract unverified)
- Adjacent userspace-paging research (useful for positioning): **PageFlex** (USENIX ATC '25) on flexible, efficient userspace delegation of page management — [ATC '25 PDF](https://www.usenix.org/system/files/atc25-yelam.pdf); and earlier work revisiting swapping in userspace with lightweight threading — [arXiv 2107.13848](https://arxiv.org/pdf/2107.13848)

### Inferences
- The `reclaim_ext` / `memcg_ext` / `bpf_proactive_reclaim` trajectory means the "pluggable policy via BPF" idea is being applied to MM *concurrently and independently* of sched_ext. A thesis that reads a paging signal in the scheduler sits precisely at the seam between these two independently-extensible subsystems — a framing that is both novel and topical, and that reviewers from the LSF/MM/BPF community will recognise.
- None of the MM-side proposals feed information *to* the scheduler; they all keep the decision inside MM. Conversely, sched_ext exposes no MM input. The absence of a cross-subsystem signal path is a structural gap, not an oversight that somebody has already filled.

### Gaps
- Merge status of the `bpf_proactive_reclaim` series (v10) and of `memcg_ext` was not established; search results did not show whether any of it landed. Check bpf-next / mainline git before claiming status.
- The `bpf_fault` paper could not be fetched (ACM DL 403). Its venue, year, and whether it touches scheduling at all are unverified; the DOI prefix suggests a 2025-26 ACM workshop proceedings. Obtain it via institutional access.

## Q8 (the decisive question). Has anyone already measured page-fault frequency inside a sched_ext scheduler?

### Takeaway
**I found no evidence that anyone has measured page-fault frequency inside a sched_ext scheduler.** Across the kernel documentation, the scx repository's own documentation, the sched-ext.com scheduler docs, LWN and Phoronix coverage, the LPC 2025 microconference material, the scx issue tracker, LKML/bpf-next archives, and academic search, no scheduler, patch, paper, talk, or blog post reads `maj_flt`/`min_flt` or any other fault counter inside a sched_ext BPF program. The claim of novelty for *measuring page-fault frequency inside a sched_ext scheduler* appears to hold, with the caveat below about search exhaustiveness.

### Cited Findings
- A targeted search for `"maj_flt"` combined with eBPF schedulers and per-task page-fault rates returned **no source describing an eBPF scheduler using `maj_flt`**; the closest match was an unimplemented proposal in an unrelated project to aggregate per-TID fault counters in a BPF map — [rand-fast issue #24](https://github.com/random6-xyz/rand-fast/issues/24)
- The kernel's sched_ext documentation does not mention page faults at all; memory appears only as BPF arena scratch storage — [kernel.org sched-ext.html](https://www.kernel.org/doc/html/latest/scheduler/sched-ext.html)
- The scx repository's `scheds/README.md` and `scheds/rust/README.md` contain no mention of memory, page faults, PSI, NUMA, cache, or pressure — [scheds/README.md](https://raw.githubusercontent.com/sched-ext/scx/main/scheds/README.md); [scheds/rust/README.md](https://raw.githubusercontent.com/sched-ext/scx/main/scheds/rust/README.md)
- `scx_lavd`'s README, the most detailed scheduler description I retrieved, names latency-criticality and CPU topology as its inputs and does not mention memory, page faults, or memory pressure — [scx_lavd README](https://raw.githubusercontent.com/sched-ext/scx/main/scheds/rust/scx_lavd/README.md)
- LWN's sched_ext coverage mentions neither page faults nor PSI; memory appears only as BPF resource limits (512-byte stack, kptr, an `alloca()` request) — [LWN 974387](https://lwn.net/Articles/974387/)
- The published 2026 sched_ext roadmap lists GPU awareness and energy-aware abstractions; memory awareness is absent — [Phoronix](https://www.phoronix.com/news/sched-ext-future-plans-2026)
- Memory pressure appears in the scx tracker only as a crash context, not a signal — [scx issue #370](https://github.com/sched-ext/scx/issues/370)
- The nearest sched_ext work using *any* pressure signal is a blog-level PoC tracking PSI for **CPU and I/O** (not memory), iowait, and dirty writeback in its userspace pacing layer — [DEV.to sched_ext batch pacing PoC](https://dev.to/xsub/pacing-batch-workloads-with-linux-schedext-an-engineering-poc-2chf)
- The nearest *academic* sched_ext memory work, CXLAimPod, uses **PMU counters and cgroup hints for bandwidth-aware CXL placement** — not fault counters, and not a back-off policy — [CXLAimPod, arXiv](https://arxiv.org/html/2508.15980v1)

### Inferences
- The novelty claim should be stated narrowly and precisely to survive review. Defensible: *"we are not aware of any sched_ext scheduler that measures per-task page-fault frequency inside the BPF scheduler and uses it as a scheduling input."* Not defensible: *"no CPU scheduler has ever reacted to paging"* (refuted by Q5 — classical load control, PFF, the Linux swap token, and US 9,465,656) or *"no sched_ext scheduler is memory-aware"* (refuted by CXLAimPod's bandwidth-aware placement).
- Two independent structural facts explain the gap and are worth stating as the reason it exists: sched_ext exposes no MM hook or memory accessor (Q1), and the BPF-for-MM effort keeps its decisions inside MM (Q7). Nobody has had a reason to bridge the two.
